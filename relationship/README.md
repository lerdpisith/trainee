## 🔍 ระดับความสัมพันธ์ (The Big Picture)

ในการออกแบบซอฟต์แวร์ ความสัมพันธ์ของวัตถุสามารถสรุปตามระดับความผูกพัน (Coupling) ได้ดังนี้:

### 1. Dependency (ความพึ่งพา) 🟡 *อ่อนแอที่สุด*
เกิดเมื่อคลาส A ใช้งานคลาส B ในช่วงเวลาสั้นๆ (เช่น เป็น parameter ในเมธอด) หากคลาส B เปลี่ยนแปลง คลาส A อาจได้รับผลกระทบ
```python
class Professor:
    def teach(self, course: Course): # Dependency on Course
        knowledge = course.get_knowledge()
        # ...
```

### 2. Association (ความเชื่อมโยง) 🟢
วัตถุหนึ่ง "รู้จัก" และเชื่อมโยงกับอีกวัตถุหนึ่งอย่างถาวรผ่านการใช้ "ฟิลด์" (field)
```python
class Professor:
    def __init__(self, student: Student):
        self.student = student # Association: Professor รู้จัก Student (ถาวร)
```

#### 💡 ความแตกต่างระหว่าง Dependency vs Association (Case Study)
จากตัวอย่างคลาส `Professor` (ศาสตราจารย์):

1.  **Dependency (ความพึ่งพา):** สังเกตที่เมธอด `teach` ซึ่งรับพารามิเตอร์เป็นคลาส `Course` หากในอนาคตคลาส `Course` มีการเปลี่ยนแปลงรายละเอียด (เช่น เปลี่ยนชื่อเมธอด) โค้ดของ `Professor` ก็จะพังตามไปด้วย เนื่องจากความสัมพันธ์ลักษณะนี้ **ไม่ได้สร้างจุดเชื่อมโยงอย่างถาวร** เป็นการเรียกใช้งานชั่วคราวผ่านอาร์กิวเมนต์ของเมธอด
2.  **Association (ความเชื่อมโยง):** สังเกตที่ฟิลด์ `student` ซึ่งทำหน้าที่เก็บบรรจุอ็อบเจกต์ของคลาส `Student` เอาไว้ อ็อบเจกต์จะถูกเก็บไว้เป็นฟิลด์ที่สามารถเข้าถึงได้ตลอดเวลาจากเมธอดใดๆ ก็ได้ภายในคลาส ซึ่งถือเป็นการสร้าง **"ความเชื่อมโยงอย่างถาวร" (Permanent link)**

กล่าวง่ายๆ คือ **Association** เป็นรูปแบบที่แข็งแกร่งกว่า **Dependency** โดยวัตถุหนึ่งจะมีสิทธิ์เข้าถึงอีกวัตถุหนึ่งอย่างถาวร (มักจะผ่านการเก็บไว้ในฟิลด์)

### 3. Aggregation (การรวมกลุ่ม) 🔵
ความสัมพันธ์แบบ "ส่วนรวม-ส่วนย่อย" (Whole-Part) โดยที่ **ส่วนย่อยสามารถดำรงอยู่ได้ด้วยตัวเอง** และคอนเทนเนอร์ไม่ได้จัดการวงจรชีวิต
- เช่น: รถยนต์ กับ คนขับ (คนขับสามารถเดินไปที่อื่นหรือขับรถคันอื่นได้)
```python
class Car:
    def __init__(self, model):
        self.model = model
        self.driver = None # Aggregation: รับ Object จากภายนอกมาเชื่อมโยง
```

### 4. Composition (องค์ประกอบ) 🟣
ความสัมพันธ์แบบ "ส่วนรวม-ส่วนย่อย" ที่เข้มงวด โดยที่ **ส่วนย่อยจะสลายไปพร้อมกับคอนเทนเนอร์** (คอนเทนเนอร์จัดการ Life Cycle)
- เช่น: มหาวิทยาลัย กับ ภาควิชา (ถ้ามหาวิทยาลัยถูกยุบ ภาควิชาก็หายไปด้วย)
```python
class University:
    def __init__(self, name):
        self.name = name
        # Composition: สร้าง Object ภายในคลาสเอง และจัดการวงจรชีวิต
        self.departments = [Department("Computer Science")]
```

#### 💡 ความแตกต่างระหว่าง Aggregation vs Composition
ความแตกต่างสำคัญของความสัมพันธ์แบบ "ส่วนรวม-ส่วนย่อย" (Whole-part relations) อยู่ที่ **"ความสามารถในการดำรงอยู่ด้วยตัวเอง"** และ **"การรับผิดชอบวงจรชีวิต"**:

1.  **Aggregation (การรวมกลุ่ม):**
    *   วัตถุทำหน้าที่เสมือน "คอนเทนเนอร์" (Container) ที่รวบรวมวัตถุอื่น
    *   ส่วนประกอบ **ดำรงอยู่ได้ด้วยตัวเอง** และเชื่อมโยงกับคอนเทนเนอร์หลายตัวได้
    *   คอนเทนเนอร์ **ไม่ได้จัดการวงจรชีวิต** ของส่วนประกอบ
2.  **Composition (องค์ประกอบ):**
    *   เป็นรูปแบบที่เข้มงวดกว่า ส่วนประกอบ **ดำรงอยู่ได้ก็ต่อเมื่อเป็นส่วนหนึ่งของคอนเทนเนอร์เท่านั้น**
    *   คอนเทนเนอร์มีหน้าที่ **จัดการวงจรชีวิต (Life cycle)** ของส่วนประกอบทั้งหมด (ถ้าคอนเทนเนอร์ตาย ส่วนประกอบตายตาม)

กล่าวง่ายๆ คือ **Aggregation** คือการรวมกลุ่มแบบหลวมๆ (อิสระต่อกัน) ส่วน **Composition** คือการประกอบรวมกันอย่างแนบแน่น (แยกออกจากกันไม่ได้)

### 5. Implementation (การนำอินเทอร์เฟซไปใช้งาน) 🟠
คลาสกำหนดรายละเอียดการทำงาน (Implementation) ตามที่ Interface ระบุไว้
```python
class Printable(ABC):
    @abstractmethod
    def print_content(self): pass

class Document(Printable): # Implementation
    def print_content(self):
        print("Printing document...")
```

### 6. Inheritance (การสืบทอด) 🔴 *แข็งแกร่งที่สุด*
คลาสลูกสืบทอดทั้งคุณสมบัติและการทำงานจากคลาสแม่ เป็นความสัมพันธ์ที่มีความผูกพัน (Coupling) สูงที่สุด
```python
class Animal:
    def eat(self): print("Eating...")

class Dog(Animal): # Inheritance
    def bark(self): print("Woof!")
```

#### ⚠️ ข้อจำกัดและปัญหาของการสืบทอด (Inheritance)
แม้ว่าการสืบทอดจะเป็นวิธีที่ง่ายในการนำโค้ดกลับมาใช้ใหม่ แต่เมื่อระบบมีขนาดใหญ่ขึ้นจะพบปัญหาดังนี้:
*   **คลาสลูกไม่สามารถลดขนาดอินเทอร์เฟซได้:** คลาสลูกถูกบังคับให้ต้องนำเมธอดนามธรรม (abstract methods) ของคลาสแม่ไปอิมพลีเมนต์เสมอ แม้จะไม่ได้ใช้งานเลยก็ตาม
*   **ความเสี่ยงเรื่องความเข้ากันได้:** การเขียนทับ (override) เมธอด ต้องมั่นใจว่าพฤติกรรมใหม่เข้ากันได้กับคลาสแม่ (LSP) เพื่อไม่ให้โค้ดของไคลเอนต์ที่เรียกใช้พังลง
*   **การทำลายการห่อหุ้ม (Breaks Encapsulation):** รายละเอียดภายในของคลาสแม่ถูกเปิดเผยให้คลาสลูกเข้าถึงได้ ทำให้ความลับของข้อมูลเสียไป
*   **ความผูกพันที่แน่นแฟ้น (Tight Coupling):** คลาสลูกผูกติดกับคลาสแม่อย่างมาก การเปลี่ยนแปลงเพียงเล็กน้อยในคลาสแม่อาจทำให้คลาสลูกพังได้
*   **การขยายตัวของลำดับชั้นคลาส (Combinatorial Explosion):** หากต้องขยายความสามารถหลายมิติพร้อมกัน จะต้องสร้างคลาสลูกผสมผสานจำนวนมหาศาล (Class Explosion)
*   **มีลักษณะที่ตายตัว (Static):** ไม่สามารถเปลี่ยนพฤติกรรมของวัตถุได้ในขณะรันไทม์ ต้องสร้างวัตถุใหม่เท่านั้น
*   **ข้อจำกัดการสืบทอด:** ภาษาหลักส่วนใหญ่ (รวมถึง Python ในเชิงปฏิบัติ) มักเน้นการสืบทอดจากคลาสแม่หลักเพียงคลาสเดียว

### 💡 ทำไมควร "เลือกใช้ Composition มากกว่า Inheritance"?

**องค์ประกอบ (Composition)** เป็นทางเลือกที่ยืดหยุ่นกว่า โดยเปลี่ยนจากความสัมพันธ์แบบ **"เป็น (is a)"** มาเป็น **"มี (has a)"** (เช่น รถยนต์มีเครื่องยนต์) เพื่อแก้ปัญหาสำคัญของการสืบทอด

#### ปัญหาการขยายตัวแบบทวีคูณ (Combinatorial Explosion)
แหล่งข้อมูลยกตัวอย่าง **แอปพลิเคชันแคตตาล็อกสำหรับบริษัทผลิตรถยนต์** ที่ต้องการความสามารถที่ปรับเปลี่ยนได้ใน 3 มิติ (Dimensions):
1.  **ชนิดของยานพาหนะ:** รถยนต์ (Car) หรือ รถบรรทุก (Truck)
2.  **ชนิดของเครื่องยนต์:** ไฟฟ้า (Electric) หรือ สันดาป (Combustion)
3.  **ระบบควบคุม:** ขับด้วยคน (Manual) หรือ ออโต้ไพลอต (Autopilot)

หากใช้ **Inheritance** ในการออกแบบ คุณจะต้องสร้างคลาสลูกเพื่อรองรับ "ทุกๆ การประกอบกัน" ของคุณสมบัติเหล่านี้เข้าด้วยกัน (2x2x2 = 8 คลาส) เช่น `AutopilotElectricTruck` หรือ `ManualCombustionCar` และคลาสอื่นๆ ให้ครบทุกความเป็นไปได้ ซึ่งจะทำให้ลำดับชั้นของคลาสบวม (Class Bloat) จนมีขนาดใหญ่โตเกินความจำเป็น และเกิดโค้ดซ้ำซ้อนมหาศาล

#### ประโยชน์ของ Composition:
1.  **การแยกมิติของการขยายความสามารถ (Separation of Dimensions):** แทนที่จะสร้างคลาสผสมทุกมิติ เราแยกมิติ "เครื่องยนต์" และ "ระบบควบคุม" ออกมาเป็นอินเทอร์เฟซอิสระ
2.  **การมอบหมายงาน (Delegation):** แทนที่วัตถุจะทำทุกอย่างเอง มันสามารถมอบหมายหน้าที่เฉพาะทางไปให้วัตถุส่วนประกอบ (Component) ที่มันบรรจุไว้จัดการแทนได้
3.  **ความยืดหยุ่นขณะรันไทม์ (Runtime Flexibility):** คุณสามารถ **เปลี่ยนแปลงพฤติกรรมของวัตถุได้ตลอดเวลา** เพียงแค่สลับวัตถุส่วนประกอบตัวใหม่มาแทนที่ตัวเดิม (เช่น สลับจาก Autopilot เป็น Manual ได้ทันที)
4.  **ลดความซ้ำซ้อน:** ไม่ต้องสร้างคลาสลูกจำนวนมากเพื่อรองรับทุกการผสมผสานความสามารถ (Mix and Match)
5.  **สอดคล้องกับ Design Pattern:** โครงสร้างนี้เป็นพื้นฐานของ **Strategy Pattern** (กลยุทธ์) ที่จะช่วยให้เราสลับอัลกอริทึมการทำงานได้ง่าย

### 🚀 Composition vs Inheritance (ตัวอย่างการเปรียบเทียบ)

ดูตัวอย่างการออกแบบระบบยานพาหนะที่ต้องการความยืดหยุ่นสูงใน `composition_vs_inheritance.py`:

**แบบ Inheritance (Class Explosion - 8 คลาส!):**
```python
class Car: pass
class ElectricCar(Car): pass
class AutopilotElectricCar(ElectricCar): pass
# ... ต้องสร้างคลาสย่อยทุกรูปแบบการผสมผสาน (2x2x2)
```

**แบบ Composition (ยืดหยุ่นกว่า - แยกมิติชัดเจน):**
```python
class Vehicle:
    def __init__(self, brand, model, engine, control):
        self.brand = brand
        self.model = model
        self.engine = engine   # Vehicle HAS AN engine
        self.control = control # Vehicle HAS A control system

    def set_control(self, new_control):
        self.control = new_control # เปลี่ยนได้ทันทีขณะรันไทม์! (Runtime Flexibility)

# มิติ 'ชนิดของยานพาหนะ' ยังคงใช้ Inheritance พื้นฐานได้
class Car(Vehicle): pass
class Truck(Vehicle): pass
```

## 🏥 ตัวอย่างเชิงปฏิบัติ: ระบบโรงพยาบาล (`practical_example.py`)

เพื่อให้เห็นภาพการทำงานจริง ไฟล์นี้ได้รวมความสัมพันธ์ต่างๆ ไว้ในระบบเดียว:
- **Hospital (Aggregation)** มี **Doctors** (หมออยู่ได้แม้ไม่มีโรงพยาบาลนี้)
- **Hospital (Composition)** มี **EmergencyRoom** (ER ถูกสร้างและสลายไปพร้อมโรงพยาบาล)
- **Doctor (Association)** รู้จักกับ **Patient**
- **Doctor (Dependency)** เรียกใช้ **PharmacyService** เพื่อสั่งยา
- **Surgeon (Inheritance)** สืบทอดมาจาก **Doctor**
- **Doctor (Implementation)** ทำงานตามมาตรฐานของ **Staff** (Interface)
